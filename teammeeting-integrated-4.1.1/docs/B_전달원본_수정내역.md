# B 파트 수정 내역 (장소 · 투표 · 확정)

작성일: 2026년 11월 11일
기준 문서: 개발 계획서 3·5장, `docs/B_개발_시작.md`
대상: A (연결할 주소와 화면 규칙을 확인하는 용도)

## 1. A가 알아야 할 것

### 요청 주소 (명세와 동일하게 맞춤)

| 방식 | 주소 | 보내는 값 | 처리 후 이동 |
|---|---|---|---|
| GET | `/meetings/{id}/coordination` | - | 장소·투표·확정 화면 |
| POST | `/meetings/{id}/places` | `name`, `memo` | 같은 화면 |
| POST | `/meetings/{id}/votes` | `placeId` | 같은 화면 |
| POST | `/meetings/{id}/confirm` | `slot`(예: `2026-11-12T15:00`), `placeId` | `/meetings/{id}/result` |
| GET | `/meetings/{id}/result` | - | 확정 결과 화면 |

### A 화면에서 연결할 일

- 모임 상세에서 `/meetings/{id}/coordination` 으로 가는 링크를 달아 주세요. 확정된 모임은 `/meetings/{id}/result` 링크도 필요합니다.
- B 화면의 "← 홈으로" 링크는 모임 상세 주소가 정해지지 않아 `/` 로 두었습니다. 주소가 정해지면 `coordination/index.mustache` 의 해당 링크를 바꿔 주세요.
- 참여자 확인과 확정 여부 확인은 `MeetingAccess.requireMember(id, email, write)` 를 그대로 사용합니다. A 쪽 시간 수정도 같은 방식이면 확정 직전·직후 요청이 한 줄로 처리됩니다.

### 공통 파일은 수정하지 않았습니다

`partials/header`, `partials/footer`, `partials/csrf`, `SecurityConfig`, `WebAdvice`, `MeetingAccess`, 엔티티는 이번에 바꾸지 않았습니다. (계획서의 "공통 파일 수정은 먼저 공유" 규칙)

## 2. 무엇이 문제였고 왜 고쳤나

| # | 문제 | 왜 문제인가 | 수정 |
|---|---|---|---|
| 1 | 모든 POST 폼에 CSRF 토큰이 없었음 | Spring Security 기본 설정에서는 토큰 없는 POST가 모두 403으로 거부된다. 장소 등록, 투표, 확정이 화면에서 동작하지 않는다. | 모든 폼에 `{{>partials/csrf}}` 추가 |
| 2 | 주소가 `/meetings/{id}/coordination/places` 등으로 한 단계 깊었음 | 명세(`/meetings/{id}/places` 등)와 달라서 A가 명세대로 연결하면 404가 난다. `/result` 주소와 화면도 없었다. | 명세대로 주소 정리, 결과 화면 추가 |
| 3 | 장소 목록 조회에 참여자 확인이 없었음 | 계획서 5장 "비참여자는 모임 데이터에 접근하지 못함"을 위반한다. 로그인만 하면 남의 모임 장소를 볼 수 있다. | 조회도 `requireMember(.., false)` 로 확인 |
| 4 | 쓰기에서 잠금 없이 `findById` 사용 | 같은 계정의 동시 투표, 반복 확정 요청이 겹칠 수 있다. 계획서 5장 "동시 요청" 항목과 명세의 공통 규칙(`requireMember(.., true)`)을 지키지 못한다. | 모든 쓰기 서비스가 `requireMember(.., true)` 로 시작 (모임 행 잠금 + 참여자 + OPEN 확인) |
| 5 | 표 변경을 "기존 표 삭제 후 새 표 저장"으로 구현 | 같은 트랜잭션에서 저장이 삭제보다 먼저 실행되어 `uk_vote`(모임+회원) 제약에 걸린다. 표 변경이 오류가 될 가능성이 높다. | 기존 표 행의 장소만 바꿈. 결과는 같다 (이전 후보 -1, 새 후보 +1) |
| 6 | 다른 모임의 장소 번호로도 투표·확정이 가능 | 명세에서 B가 서비스에서 검증하라고 한 항목이다. | `findByIdAndMeetingId` 로 같은 모임의 장소만 허용 |
| 7 | 확정을 모임의 누구나, 어떤 장소든 할 수 있었음 | 계획서: 팀장만, 전원 응답 완료, 공통 시간 존재, 1표 이상 받은 최다 득표 장소만 확정. 확정 날짜와 시작·종료 시각도 저장해야 한다. 기존 코드는 상태와 장소만 저장했다. | 위 조건을 모두 서버에서 검사하고, 날짜·시작·종료·장소·상태를 한 트랜잭션에서 저장 |
| 8 | 공통 시간 계산이 없었음 | 확정 조건과 확정 시간 저장에 필요하다. | 전체 참여자 기준, 09~20시 시작 1시간 슬롯으로 계산 (`CoordinationService`) |
| 9 | 화면이 공통 레이아웃 없이 자체 CSS를 사용 | 공통 header/footer를 쓰지 않아 로그아웃 버튼과 Bootstrap이 빠졌다. 모든 사용자에게 투표와 최종 확정 버튼이 노출되었다. 일정 지연 시 "화면 꾸미기를 줄인다"는 원칙과 달리 코드 안에 스타일이 섞여 있었다. | 공통 partial과 Bootstrap 클래스만 사용. 팀장에게만 확정 폼 표시, 확정 후 후보 등록·투표 폼 숨김 |
| 10 | 엔티티를 화면에 그대로 전달 | `spring.jpa.open-in-view=false` 이면 화면에서 지연 로딩 오류가 날 수 있다. 득표수·내 선택 표시에도 맞지 않는다. | 서비스에서 화면 전용 모델(`CoordinationView`, `ResultView`)로 변환 |

## 3. 계획서와 다르거나 남아 있는 부분 (이유 포함)

| 항목 | 내용 | 이유 |
|---|---|---|
| `confirm` 의 `slot` 값 | 명세 표에는 주소만 있고 보내는 값이 없다. `slot` 을 추가했다. | 계획서가 "팀장이 공통 시간과 최다 득표 장소를 선택해 확정"하고 "날짜와 시작·종료 시각을 모두 저장"하라고 한다. 시간을 고르는 값이 없으면 저장할 수 없다. |
| 표 변경 방식 | 삭제 후 추가 대신 기존 행 수정 | 위 5번. 동작 결과는 계획서와 같고 구현 방식만 다르다. |
| 공통 시간 계산 시점 | 계획서 6~8일 차 작업인데 먼저 구현 | 확정 조건에 필요해서 함께 만들었다. 인원순 추천은 계획서대로 추가 기능으로 남겼다. |
| 이전 파일 | `templates/coordination.mustache` 는 내용을 비운 상태 | 파일 삭제 권한이 없어 안내 주석만 남겼다. 직접 삭제하면 된다. |
| `MeetingMemberRepository.existsByMeetingIdAndUserId` | B는 더 이상 사용하지 않는다. | 이전에 오류를 피하려고 추가된 메서드다. 지워도 되고 두어도 된다. |
| 동시 요청 테스트 | 아직 없음 | 계획서 12~13일 차 작업. 현재 테스트는 한 트랜잭션 안에서 규칙만 확인한다. |
| 화면 흐름 점검 | 아직 안 함 | A의 회원가입·모임 생성이 연결된 뒤 두 계정으로 점검한다. |
| header 문구 | `partials/header` 의 제목이 "공통 기반" 으로 되어 있음 | 공통 파일이라 수정하지 않았다. A가 정리해 주세요. |

- 화면: A 연결 후 두 계정으로 장소 등록, 투표 변경, 팀장 확정, 결과 화면을 확인한다.
